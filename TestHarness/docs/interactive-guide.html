00

Start here — what a test harness actually is

the scaffolding, not the test

A test harness isn't a single Simulink block, and it isn't a test either. It's the reusable scaffolding around models: a library of standard inputs you can feed anything, automated checks that turn output into pass/fail, and a record of every run so you can tell what changed. Once it exists, adding a seventh scenario is four lines of code. Without it, every check is a fresh half-hour of wiring scopes and squinting at waveforms.

Why this is the integration lead's job

By W8 you'll receive five models built independently by five people who never ran them against each other. If something misbehaves then, "why doesn't the system work" has no answer — the fault could be anywhere. With a harness, every subsystem is validated against its own written spec before it touches the shared DC bus, so a W8 failure is almost certainly the integration, not a hidden bug in someone's PV model.

Everything below was built and verified against a model simple enough to learn from in one sitting, but real enough that the harness transfers directly: a DC-link voltage loop — the same "DC volt loop" on Aqib's W8–W9 row of the team timeline. Learn this, and you're not learning a toy — you're learning the actual harness you'll point at five real subsystems.

01

The plant — what the model under test actually does

C·dVdc/dt = i_src − i_out

The DC bus is one capacitor with two currents fighting over it: i_src pours in from the PV and wind stages, i_out is pulled out by the grid-side inverter. The controller's only lever is commanding i_out — it regulates voltage by controlling a current.

Inner current loop is collapsed to its dominant first-order behaviour (τᵢ = 1 ms) rather than modelled in full — standard practice when the fast loop is much faster than the loop you're actually studying.

Every number in this diagram lives in one file, config/harnessParams.m — C = 2200 µF, τᵢ = 1 ms, Vdc_ref = 700 V, Imax = 20 A. Nothing is typed into a block dialog by hand. A test in §06 exists specifically to catch anyone who does.

02

Sign convention — the one line worth memorising

e = Vdc − Vdc_ref, not the textbook way round

The error is defined measured minus reference — backwards from the textbook e = ref − measured. It's not a typo.

The plant carries a hidden negative sign: pulling more current out makes the voltage go down. Using the textbook convention as well would stack two inversions and force negative PI gains to stay stable — which reads as a bug to anyone reviewing it. Flipping the error definition once cancels the plant's sign, so the gains stay positive.

Sanity check by perturbation — more reliable than sign-chasing

Vdc rises above setpoint → e > 0 → PI increases i_out → more current pulled from the capacitor → Vdc falls back. Negative feedback, confirmed by tracing consequences, not signs.

In the model this is the Error Sum block with signs "-+": input 1 (Vdc_ref) subtracted, input 2 (Vdc feedback) added. If you ever port this pattern to a new loop, this is the first thing to re-derive — never copy the sign convention blind.

Why matlab.unittest, not Simulink Test's Gherkin format

Simulink Test is licensed on this install, but every teammate should be able to run these tests from plain MATLAB — no extra tooling required. matlab.unittest is native, runs from the Test Browser, and supports parameterized tests, which fits a scenario × variant matrix exactly. Both approaches were later built and measured head-to-head — see §09 for what each one actually catches and misses.

Scenario library — six loads, not all checks apply

Every scenario declares which requirements are meaningful for it. During overload, the source pushes 60 A into an inverter that may only remove 20 A — the bus voltage must run away past 4.5 kV. That's physics, not a defect. A harness that asserted regulation there would fail on every single run, everyone would learn to ignore the red mark, and the one check that actually matters — did the current limit hold — would drown in noise.

05

Tuning — how ωc = 200 rad/s was chosen

the spec was written before the controller was tuned

That ordering is the whole point — a spec written after the fact just describes whatever you happened to build. Both variants share one rule: Kp = C·ωc, Ki = Kp·ωc/10. Only ωc changes.

ωc (rad/s)Peak dev.Settle
4013.66%0.450 s
100 rejected5.54%0.187 s
150 rejected3.74%0.101 s
200 chosen2.85%0.062 s
4001.56%0.015 s
  • ωc = 100 rejected — 5.54% overshoot, just past the 5% limit. The first tuning attempt failed its own spec: the harness earned its keep on run one.
  • ωc = 150 rejected too — met overshoot, but settled at 100.5 ms against a 100 ms limit. A design that only just passes is a design that fails after the next change.
  • ωc = 200 chosen — real margin on both (2.85% vs 5%, 62 ms vs 100 ms), phase margin ≈ 73°, and stays 5× below the inner current loop's implied bandwidth (1/τᵢ = 1000 rad/s) — comfortable separation for the two-time-scale assumption the model relies on.

sluggish uses ωc = 40 — fails both overshoot and settling by a wide enough margin that there's no ambiguity about whether the harness caught it.

07

Spec vs. regression — two different questions

"is it acceptable?" vs. "did it change?"

This is the single most useful idea in the whole harness. Spec tests ask: is this acceptable? Regression baselines ask: did this change? You need both — here's the proof.

The DC-link capacitance was nudged up 5% and everything re-run. Every spec test still passed — the design was still acceptable. But the baseline caught real drift:

That is exactly the situation W8–W10 will put you in, with five people editing five models. Most changes will still pass spec. The question you actually need answered is "which of you changed something, and was it on purpose?" The regression tolerances aren't "how much error is acceptable" — the spec already covers that — they're "how much change is worth telling a human about."

Caution

Saving a baseline blesses the current behaviour as correct. A baseline saved from a broken run makes every future regression check agree with the breakage — save it deliberately, never casually.

Running it

start with setupHarness — always

One command puts the session in a state where everything else works. Run it first, once per MATLAB session.

Set up the session (do this first)setupHarness
Full report + regression checkrunAll
Same, plus a shareable HTML reportrunAll(Report = true)

Inspect one scenario[out,P,meta,ds] = runScenario("cold_start")
Record a new baselinerunAll(SaveBaseline = true)
Compare runs visuallySimulink.sdi.view
Rebuild the model from sourceP = harnessParams(); buildDCLinkLoop()

Expected clean result: 9/9 tests pass, 6/6 scenarios meet spec, no drift.

setupHarness is not bookkeeping. It fixes four things that each cost an afternoon to diagnose the first time:

  1. Paths. Adds the five source folders.
  2. Build artifacts out of OneDrive. Simulink defaults its cache to the current folder. One test run dropped ~1.1 MB of binary cache into the synced tree — churn that reaches five teammates and merges for none of them. It now goes to %LOCALAPPDATA%.
  3. P into the base workspace. Every block references P.ctrl.* rather than a literal, so the model cannot compile without it.
  4. The OneDrive read-only flag. OneDrive marks synced folders read-only. Writes actually succeed, but Simulink Test believes the flag and refuses to run.
Trap

addpath(genpath("TestHarness")) adds nothing if you are already standing inside TestHarness — it looks for a nested folder of the same name, finds none, and fails silently. The first symptom is Unrecognized function or variable 'runAll'. Use setupHarness.

Why P hides

runAll and the test suite work without P in the base workspace, because runScenario injects it through SimulationInput.setVariable. Anything that compiles the model directly — model_test, Update Diagram, just opening it — does not, and Simulink reports only "compilation failures" without naming a cause.

09

Two ways to test — and what each one misses

measured, not argued

MathWorks ships a second way to test this model: Gherkin — plain-English scenarios in a .feature file, run through model_test. It is worth knowing why the harness does not simply use it instead.

The same six scenarios, the same spec limits, were written both ways and run against the same model. Both catch the deliberately-detuned sluggish controller. They are not equivalent.

Gherkin's signal generators are const() and step() — that is the whole vocabulary. So two scenarios cannot be written at all: source_ramp needs a ramp, and cold_start needs the bus to start at 650 V, which is an initial condition, not an input.

That gap is measurable. Decision coverage of the model:

The missing outcome is the lower branch of Current_Limit [Saturate] — and the only scenario that drives it is cold_start, the one Gherkin cannot express. The scenarios it drops are precisely the ones carrying the extra coverage.

The real cost

A .feature file cannot read harnessParams.m, so every limit becomes a typed number — Vdc == [693 .. 707] is 700 ± 7 written by hand. Change the tolerance in one place and the Gherkin tests keep silently checking the old value. That is the exact failure the parametersAreSingleSourceOfTruth test exists to prevent.

Where Gherkin wins

Its failure output is genuinely better: the condition in plain English, the actual signal ranges, a saved .mat of the run, and copy-paste code to inspect it. Draft mode runs in about three seconds. When you are hunting one specific bug, that loop is hard to beat.

Verdict: complementary, not either/or. matlab.unittest is the spec-and-regression backbone — full coverage, one source of truth, baselines, reports. Gherkin is the fast loop for chasing a particular bug. Run it with setupHarness(Toolkit = true), then model_test on tests/dcLinkLoop.feature.

10

Extending it — to a teammate's model

four things change, nothing else does

The harness is deliberately generic. To validate Belal's PV model or Aqib's SRF-PLL, four things change:

  1. Write the spec first, in harnessParams.m, before looking at their model. For the PLL: lock time, steady-state phase error, frequency overshoot on a phase jump. For PV MPPT: settling time and percentage of available power captured.
  2. Add scenarios to createTestInputs.m — grid voltage sag/swell, a phase jump, a frequency ramp for the PLL; irradiance and temperature profiles for the PV.
  3. Declare which requirements apply to each scenario (meta.applies).
  4. Add the metrics to evaluateSpec.m.

runScenario, runAll, and the whole regression mechanism carry over unchanged.

Do this before W8

The highest-value item in that list, applied across the whole team: pin down exactly what signals each subsystem exposes at its boundary — names, units, sign conventions, sample rates — while everyone is still building. Mismatched interface assumptions are what actually blow up integration week, far more often than the control theory does. This isn't hypothetical for this project: a real debugging session lost real time to a PMSG initial condition given in rpm while the connected block expected rad/s. Neither model was wrong. The interface between them was never written down.

Exercises — go break it

reading the harness and owning it are different things

  • Break it on purpose.Set P.ctrl.Kp to P.ctrl.Kp/10 and run runtests. Do the failure messages tell you what to do?
  • Loosen a spec until a real failure passes.Set overshootPct to 20 and run the sluggish variant. Notice which test objects — and why that test exists.
  • Add a scenario.A double disturbance: source steps up at 0.2 s, then a cloud at 0.35 s. Which requirements apply? What should evalStart be?
  • Add a metric.Peak dVdc/dt — the rate of voltage change, which matters for capacitor stress. Add it and give it a spec limit.
  • Find the anti-windup bug.The saturation block limits the output but the PI integrator doesn't know it. Drive it hard enough to saturate for a sustained period and watch the integrator wind up.
  • Use SDI properly.Run nominal, then sluggish, then overlay the two Vdc traces in Simulink.sdi.view. This is what belongs in the W11 report.
